It extends the [first suite](../initial/README.md) at `829e7bd`, based on [the research context at 08188ff](https://github.com/nousentllc/riemann-hypothesis/blob/08188ff0c6dd02dfec0bd65d30765862e9db56b7/research/uriel/PROOF_CONTEXT.md).

This establishes a local check of the implication from arbitrarily late one-sided windows to a zero-free region. The arithmetic construction that supplies those windows lies outside this build. ## Run the finite suite

From the repository root, with Python 3.12 or 3.13 and mpmath 1.3.0:

```sh
python3 -m venv /tmp/uriel-rh-python
/tmp/uriel-rh-python/bin/python -m pip install mpmath==1.3.0
EXP=research/uriel/experiments/second
/tmp/uriel-rh-python/bin/python -B "$EXP/run.py" --out /tmp/uriel-rh-numbers
```

The script executes the experiments and their tests. The output directory contains six scientific JSON files, a hash manifest and the test transcript. Integers decide the rank, residue and projection comparisons. The complex probes use 70 and 110 decimal digits, and the prime-window estimates use 60 and 90. The reported accuracy comparison is computed before rounding results to 20 significant digits. No random seeds, network or Lean installation are required for this run. [Recorded numerical environment](results/numerical_run.json)

To repeat the cross-run comparison, use the same command with a second Python interpreter and another output directory. Run the first suite in its separately pinned environment, using its `--out` option. Then run `verify_replays.py --other SECOND_OUTPUT --first-round FIRST_SUITE_OUTPUT --out COMPARISON.json` from this directory. It verifies every compared file against the stored scientific outputs and checks both test exits. [Recorded comparison](results/reproduction.json)

## Rebuild the original analytic closure and inspect its terms

These commands require a git checkout with the original pin available. A partial clone fetches the required original blobs on first access. Use the published Lean v4.33.1 distribution for your platform, or install the pinned toolchain through elan as below. The full Mathlib binary cache and the toolchain used about 10 GiB on this run.

```sh
ROOT=$(git rev-parse --show-toplevel)
EXP="$ROOT/research/uriel/experiments/second"
TRIAL=$(mktemp -d)
elan toolchain install leanprover/lean4:v4.33.1
LEAN_DIR=$(elan run leanprover/lean4:v4.33.1 lean --print-prefix)
git clone --depth 1 --branch v4.33.1 https://github.com/leanprover-community/mathlib4.git "$TRIAL/mathlib"
(cd "$TRIAL/mathlib" && PATH="$LEAN_DIR/bin:$PATH" "$LEAN_DIR/bin/lake" exe cache get Mathlib)
python3 -B "$EXP/formal.py" prepare --work "$TRIAL/work" --out "$TRIAL/evidence"
python3 -B "$EXP/formal.py" build --work "$TRIAL/work" --out "$TRIAL/evidence" --toolchain "$LEAN_DIR" --mathlib "$TRIAL/mathlib"
python3 -B "$EXP/formal.py" audit --work "$TRIAL/work" --out "$TRIAL/evidence" --toolchain "$LEAN_DIR" --mathlib "$TRIAL/mathlib"
python3 -B "$EXP/formal.py" finish --work "$TRIAL/work" --out "$TRIAL/evidence" --toolchain "$LEAN_DIR" --mathlib "$TRIAL/mathlib"
```

The runner reads source bytes with `git show`, checks package revisions against the original manifest and uses the original Lean options. It adds a single-worker limit and writes generated sources and compilation products only under the scratch directory. Each operation records its return status. The axiom inventory, actual proof-value references and comparison with the earlier lexical graph are generated by the audit stage. Run the build in a fresh scratch directory to preserve its provenance. [Original build configuration](https://github.com/nousentllc/riemann-hypothesis/blob/40e56bab026552e089d7afcfeff08d2defb9c005/lakefile.toml)

## Compare compiled files with the external manifest

The additional packaging control downloads a 29 MB public list, verifies its SHA-256 against the published digest and compares only the analytic modules. It also compiles the same root with and without the original Lake package tag. The full option rebuilds the closure with that tag in an isolated dependency directory and kernel-replays its endpoint. With the variables from the preceding commands:

```sh
curl -fL https://math.mit.edu/~drew/grh/project-oleans.sha256 -o "$TRIAL/project-oleans.sha256"
python3 -B "$EXP/object_compare.py" --all-packaged --manifest "$TRIAL/project-oleans.sha256" --work "$TRIAL/work" --out "$TRIAL/evidence" --toolchain "$LEAN_DIR" --mathlib "$TRIAL/mathlib"
python3 -B "$EXP/object_compare.py" --source-label-controls --manifest "$TRIAL/project-oleans.sha256" --work "$TRIAL/work" --out "$TRIAL/evidence" --toolchain "$LEAN_DIR" --mathlib "$TRIAL/mathlib"
python3 -B "$EXP/object_compare.py" --replay-matched --manifest "$TRIAL/project-oleans.sha256" --work "$TRIAL/work" --out "$TRIAL/evidence" --toolchain "$LEAN_DIR" --mathlib "$TRIAL/mathlib"
```

The filename control supplies the same pinned bytes on standard input twice, varying the source filename between the relative path and the filename documented by the external build. The final command rehashes every resulting module against the externally published value and calls the pinned kernel checker on each matching object. All generated files stay in the scratch or evidence directory. [External verification record](https://math.mit.edu/~drew/grh/)
